Executive Summary
The Zero Shot Balancer is a 3D printed and embedded software robot that has an objective to remain upright. This goal is fulfilled with self balancing control that is simulated in a virtual environment and trained through machine learning evaluations. The problem that will be investigated in this experiment will be if a controller for a real world physical robot can accurately be trained in a simulated environment. It will uncover how well a simulated self balancing robot can be trained using machine learning and then seeing if that training is transferred to a physical robot engineered by the team. Therefore, the main goal of the team is to transfer a trained model without any additional real world testing to a real robot which is where the team created the “zero shot” balancer title for the project. The elimination for needing additional training can have numerous applications in real world computing and engineering including in hazardous environments, unpredictable environments, or when training cannot be conducted in the real world at the scale in which it can in a simulated one. 
The team has taken the approach to use MuJoCo files with Gymnasium to build a simulated robot modeled off the physical robot. With these files the team trains a baseline policy for the simulations then changes different variables in the simulation to represent different environments the robot could encounter. Examples of these varied conditions could be changes in friction, center of mass, or motor strength. The baseline and fine tuned model will be evaluated on different metrics determined by the team. In terms of the physical robot design, custom 3D printed chassis hold together electronics needed, battery packs, and motors used for the wheels. The reinforcement learning model will be deployed onto an ESP32 microcontroller which will control the motor movements. The robot’s tilt, wheel rotations, and motor speeds will be collected by the IMU and motor encoders. It is the critical communication between the ML teams and embedded teams as the simulations will match the physical robot in terms of dimensions, mass, sensor inputs, and motor controls. The test will be once those are all combined if the robot is able to maintain balance in a real world environment without any real world training, only simulated. In the end of the experiment, the deliverables from the team will include a fully integrated robot, simulated environment mirroring the real world, evaluation results, and documentation for how it could be recreated for robotics in many different applications. The team will be documenting this process and plans to share this documentation and an open source repository to the public so that other developers can use this experiment in different applications across robotics.  
Problem Statement
Reinforcement learning (RL) policies frequently fail when deployed to altered or abnormal physical conditions. This project implements a framework to benchmark and improve zero-shot physical generalization using an open-source design for a two-wheeled balancing robot. The team simulates the robot in MuJoCo via Farama Foundation’s Gymnasium (formerly belonging to OpenAI) to train it to move forward as long as possible without falling over across randomized physical conditions -- including surface friction, terrain slope, payload, center of mass offsets, motor strength, and aerodynamic drag. The  approach focuses on training over a structured subset of slight dynamic variations to achieve a reliable zero-shot generalization across naturally varied physical environments. The target users are robotics researchers and control engineers seeking to benchmark zero-shot sim-to-real transfer.

User Stories
The team came together for an understanding of who the experiment will be helpful for. The following are the user stories that are created to understand the different features and findings the Sim-to-Real problem is looking to solve. 
* US-01: As a roboticist, I want to run a baseline policy in simulation so that I can establish a reference for comparing other policies. 
* US-02: As a roboticist, I want to vary physical parameters so that I can evaluate how well a policy handles unfamiliar physical conditions. 
* US-03: As a roboticist, I want to evaluate baseline and fine-tuned policies using the same benchmark so that I can compare their performance consistently. 
* US-04: As a controls engineer, I want to deploy a simulation-trained policy to the physical robot so that I can evaluate transfer without additional real-world training.

General Concept of Operations
________________


The target users for the project are robotics researchers and control engineers interested in evaluating zero-shot sim-to-real transfer. By using the proposed system, users will be able to run reinforcement learning policies in simulated environments and evaluate how well they perform when physical conditions are different from the ones used during training. The simulated environment will be provided by MuJoCo through Gymnasium. This environment will allow users to test the policy under different conditions, like gravity and friction, and observe how the robot's behavior changes. For example, these environments will allow users to test the policy’s ability to maintain the robot's balance and forward movement under different physical conditions.
For simulation evaluation, users will run automated benchmarking scripts to test baseline and fine-tuned policy checkpoints. The checkpoints will be tested using the project's standardized out-of-distribution MuJoCo environment. This will allow users to evaluate the performance of the models across different simulated physical conditions. At the time of running these benchmarks, users will be able to observe how the baseline and fine-tuned models perform when tested outside of their original training conditions.
Another way that researchers will be able to benefit from the project is through the open-source repository. Users will be allowed to clone the repository and insert their own reinforcement learning models to replicate the training and evaluation process. This will allow them to test their own models using the same simulated environments and benchmarking process provided by the project. By having access to the repository, other researchers can reproduce the project's process and evaluate how their own models perform under the different simulated conditions.
In addition, using the same evaluation process allows different reinforcement learning models to be tested under the same conditions. Instead of each model being evaluated using a different setup, researchers can use the project's environment and benchmarking process to observe how different models respond to the same physical changes. This is an important detail because it makes it possible to compare results from different approaches with the same baseline and create a better understanding of how the models generalize when the simulated conditions are different.
Finally, another way for researchers and engineers to use the project would be through physical verification. In this case, the users will be able to inspect live telemetry and observe physical testing runs while the robot attempts to maintain upright balance and move forward for a maximized distance. This characteristic will give users the ability to see the effectiveness of the model in a real physical environment rather than just relying on the simulations.
During physical verification, evaluators will be able to observe the robot while the policy is tested under the different real-world conditions included in the project. The robot will attempt to remain upright and continue moving forward while conditions like friction variations, external push disturbances, payload shifts, or motor degradation are introduced. The engineer or researcher will also be able to check the live telemetry and the physical behavior of the robot throughout these tests. Since no additional real-world retraining will be performed, this process will help evaluate whether the policy can maintain its behavior when transferred directly from simulation to the physical system.
The performance is measured by how long and how far the robot moves forward without falling, while being exposed to randomized conditions. Fine-tuned policies are expected to outperform baseline policies on out-of-distribution environments, and comparing physical results with simulated results quantifies the sim-to-real gap. Testing will take place under controlled conditions while maintaining zero-shot evaluation, meaning that the model will rely on what it learned during simulation rather than being retrained on the physical hardware.

Technical Outline
Machine Learning
Simulation purpose and architecture
   1. Role in the project
The robot must remain upright while following requested speed and heading commands. These objectives interact because wheel acceleration used to recover balance can temporarily move the robot away from its requested speed. The simulation represents these interactions so that the policy can learn from the consequences of its actions over time.


The simulation also supports controlled experiments. A baseline configuration establishes the robot's behavior under fixed conditions, while changes to friction, mass distribution, actuator strength, or disturbances provide conditions for investigating generalization. Environment configurations define the physical conditions; reinforcement learning experience is generated through interaction with those environments. Each interaction produces observations, actions, rewards, and an episode-ending signal.


The project's zero-shot objective is to transfer a simulation-trained policy without additional learning from physical deployment experience. Physical measurements and testing remain necessary to establish model parameters, align sensor and motor interfaces, and evaluate transfer. The simulation therefore supports both controller development and preparation for the physical system.


   2. Tool selection
MuJoCo supplies rigid-body dynamics, contact handling, and actuator simulation. Robot geometry, joints, inertia, and actuator properties are defined in MuJoCo's XML-based MJCF format [MuJoCo Docs]. Its Python interface fits the project's training workflow, while the existing reference controller and robot models provide a starting point for development and baseline comparisons.


Gymnasium connects this physical model to the learning algorithm through an environment interface. Each control step returns an observation, reward, termination flag, truncation flag, and information dictionary. Termination identifies a task-defined ending such as a fall; truncation identifies an external limit such as maximum episode length [Gymnasium Docs].


Stable-Baselines3 provides the reinforcement learning implementation, with Proximal Policy Optimization serving as the starting algorithm [Training Script]. The environment defines the task and physical interaction independently of the algorithm's internal training loop. Algorithm selection, reward design, and training experiments are covered in the training section of the PDD.




   3. Environment responsibilities
The implementation separates shared robot behavior from training-specific behavior. The base environment extracts robot state, constructs observations, applies wheel commands, advances the physics simulation, and detects excessive tilt. The training environment adds target scheduling and reward calculation. The MJCF files define the physical world and robot [Environment Files; Core Files] .


At each control step, the policy receives the six-element observation and produces two wheel adjustments. The environment converts those adjustments into actuator requests and advances MuJoCo through the configured physics interval. The updated state supplies the next observation and fall decision [Environment Files]. This division separates changes to the physical model from changes to the learning task.


Experiment support includes dependency management, automated tests, checkpoint saving, reward-term logging, and selected episode videos. Together, these artifacts support investigation of unexpected behavior. Reproducing a result also requires the associated model, environment settings, preprocessing, random seeds, and command schedule.


1. Robot representation and physical assumptions
   1. Geometry and coordinate conventions
The active training world contains a floor, one chassis body, and two wheel bodies. A free joint permits chassis translation and rotation, while a hinge joint connects each wheel to the chassis. The model has eight velocity degrees of freedom: six for the chassis and one for each wheel. Primitive boxes and cylinders currently approximate the robot’s structure [Core Files]. However, a CAD-derived model of the physical robot is planned to improve geometric correspondence.


The axle lies along X, and Z points upward. The environment calls rotation about X “pitch,” representing the robot’s forward and backward lean. The revised model explicitly identifies Y as the forward axis [Core Files; Environment Files]. These conventions determine how simulated orientation corresponds to the IMU mounting and firmware transformations.


The wheel hinge axes point in opposite directions. Consequently, forward travel uses opposite-signed joint velocities on the two sides. The environment calculates its combined wheel-speed measure by subtracting the right velocity from the left and dividing by two [Environment Files]. This sign convention also applies to encoder readings and motor commands during deployment.

Mass distribution matters because changing component height or placement changes the robot’s response to gravity and wheel acceleration, even when the total mass remains constant.


   3. Actuation and motor behavior
Both models use velocity actuators with a feedback gain of 4.0. A requested wheel speed produces effort according to the difference between requested and measured speed, subject to actuator limits. With the model’s unit joint transmission, the force limits correspond to wheel-joint torque limits [Core Files; MuJoCo Modeling Docs].


Requested speed and actual speed are distinct. The wheel’s response depends on torque, inertia, contact, and elapsed time. The policy therefore learns to control a system with velocity feedback. If the physical motor driver accepts pulse-width modulation, the embedded controller needs a corresponding feedback loop or conversion that preserves the meaning of the learned velocity request.


The models include wheel-joint damping but do not explicitly model motor electrical behavior or battery voltage [Core Files]. Planned motor characterization includes achievable speed, acceleration, braking, and response under load. These measurements will determine whether the simplified actuator model captures the behavior needed for balancing and movement control.
   4. Contact and simulation timing
Both worlds use downward gravity of 9.81 m/s², a physics timestep of 0.00002 seconds, and the implicit fast integrator. Each environment action advances 250 physics steps. The resulting control interval is 0.005 seconds, equivalent to 200 policy decisions per simulated second [Core Files; Environment Files]. This timing defines the simulated control rate. Execution at the same rate on the physical controller remains untested.


Wheel-floor contact pairs specify friction and solver settings. Because those pair settings determine the contact behavior, future friction experiments must modify the effective contact parameters [Core Files; MuJoCo XML Docs]. The baseline represents rigid components interacting with a flat, frictional surface. Tire deformation, chassis flexibility, and aerodynamic drag are not explicitly modeled. Observations use simulated state directly, with an episode-level pitch offset but no additional sensor-noise model [Core Files; Environment Files].

Pitch and heading are derived from the simulated body’s orientation, represented as a quaternion. Pitch rate is calculated from the change in pitch divided by elapsed simulation time. If prior history is missing or the time interval is nonpositive, the rate is returned as zero and the stored history is refreshed. Heading-error wrapping represents the shortest signed difference across the angular boundary [Environment Files].


The fixed wheel scaling is part of the policy interface. Wheel velocities with magnitude above 42.5 rad/s produce scaled observations outside the declared [−1, 1] bounds; the environment does not clip them [Environment Files].




   2. Statistical normalization
During training, Gymnasium’s observation-normalization wrapper rescales observations using running statistics. Because evaluation and deployment rely on this exact preprocessing state, each policy checkpoint must retain these statistics so they can be frozen during inference [Gymnasium Wrappers Docs].
While training currently applies normalization, checkpoint persistence and inference integration remain outstanding [Training Script]. Finalizing the overall observation interface also requires defining order, signs, units, fixed scales, and physical sensor filtering.




   3. Wheel commands
The action space has two continuous components, ordered left then right, each bounded between −1 and 1. Each component is multiplied by four and added to that wheel’s measured joint velocity to form a requested velocity. For measured velocities of 10 and −10 rad/s, actions of 0.5 and −0.5 request 12 and −12 rad/s [Environment Files].


The adjustment is relative to the latest measurement. Repeating an action while the measured velocity remains unchanged produces the same request. Once physics advances and the wheel velocity changes, the same action can produce a different target [Environment Files]. This behavior is relevant to both the action tests and the physical controller’s implementation.


Zero action requests the currently measured velocity. The velocity servo can still apply effort during the following interval to maintain that request. The environment writes requested velocities to the actuators, while MuJoCo applies the configured actuator constraints during force calculation [Environment Files; MuJoCo Modeling Docs]. Equivalent command saturation and feedback behavior must be defined for hardware deployment.


3. Episode behavior
   1. Targets and initialization
The built-in training schedule samples a base target-speed magnitude between 10 and 20 rad/s, assigns its sign, and selects a heading between −π and π. Speed begins at zero, changes to the sampled target after one second, reverses after three seconds, doubles after 4.5 seconds, and triples after 5.5 seconds. Heading remains fixed within the episode [Environment Files]. This schedule exposes the policy to starts, reversals, and increasing speed requests.


Reset samples an approximately ±2-degree offset in reported pitch. This offset affects observations, reward, and termination without physically rotating the robot. The initial physical orientation separately samples a heading about Z between −π and π and small rotations about X and Y between −0.2 and 0.2 radians. The resulting orientation is stored using MuJoCo’s scalar-first quaternion convention [Environment Files].


   2. Reward and episode endings
The reward combines an alive term with pitch, speed-tracking, heading, lean-shaping, and wheel-motion terms. It is calculated before physics advances, while the returned observation and fall decision use the state after advancement. Falls end the episode without an additional explicit terminal penalty [Environment Files].


An episode terminates when the magnitude of reported pitch exceeds 50 degrees. A separate time limit truncates episodes after 6,000 control steps, corresponding to 30 simulated seconds [Environment Files]. Distinguishing these endings allows evaluation to separate falling from completing the allotted interval. The fall threshold is an implemented task boundary whose behavior remains part of the planned episode-level testing.

The observation tests also document a pitch-rate limitation: direct subtraction across an angular wrap can produce an incorrect derivative [Tests; Environment Files]. Normal balancing episodes end before such extreme pitch angles, but the case identifies an assumption in the helper. 


   2. Planned physics validation
The next validation stage exercises commands through the complete simulation. An isolated or supported-wheel setup can establish actuator response without the competing effect of a falling chassis. Ground-contact tests can then examine travel direction, turning, slip, and the interaction between wheel acceleration and body tilt.


These tests will compare requested speed, measured speed, and actuator effort over defined intervals. Holding a fixed velocity target and repeatedly applying a measurement-relative action are different control conditions and require separate checks. Additional model checks include compiled inertial properties, initial contacts, finite state values, and timestep sensitivity.


Timestep comparisons need to preserve the policy interval by adjusting the number of physics substeps. Otherwise, numerical integration and controller timing change together. Episode tests will also cover reset consistency, the fall threshold, and time-limit truncation. A save-and-load check will verify that the same observation receives consistent preprocessing before and after checkpoint restoration.


   3. Baseline evidence and reproducibility
Historical scheduled evaluations provide preliminary evidence about tracking and falling behavior [Experiment Records]. Their interpretation depends on the checkpoint, command schedule, metric definitions, and reset rules.


For simulation comparisons, the experiment record needs to identify the physical model, environment revision, policy checkpoint, preprocessing state, seed, and schedule. This connects each result to a reproducible configuration and helps distinguish a controller change from a change in the task or physics.


5. Integration with the physical robot
   1. Physical parameters and sensor interfaces
Hardware integration requires a physical parameter record covering assembled mass, component placement, wheel dimensions, axle spacing, center of mass, inertia estimates, motor response, and surface conditions. Each value needs an identifiable source, such as measurement, CAD, or an estimate, so that model refinements can be traced to the physical design.


The policy currently receives simulated orientation and joint velocities directly [Experiment Files]. The physical system must estimate corresponding values from the IMU and encoders. A shared interface definition therefore needs coordinate frames, encoder signs, units, filtering, heading reference, command interpretation, and control timing. Representative sensor recordings can be processed through the proposed observation pipeline and compared with simulated inputs.


Heading requires particular coordination because the controller tracks a heading target. The sensing and estimation approach must establish that reference and address drift. Consistency in pitch-rate estimation and normalization is equally necessary for the physical policy inputs to retain the meaning used during training.
   2. Remaining simulation work
Immediate priorities are to complete reset and episode-behavior tests, reconcile observation bounds, preserve normalization state, and validate actuator response with physics enabled. Training and evaluation also require separate environment instances with controlled preprocessing. These tasks establish the fixed-condition simulation used for subsequent robustness experiments.


The parameter studies described in the Data Generation section already examine individual and combined physical variations using a separate reference-policy validation profile. Extending this work to the revised robot model requires completing its integration and establishing a qualified baseline. The broader varied-physics benchmark remains under development, with parameter selection and the separation of training, validation, and test conditions addressed in the Data Generation and Performance Evaluations sections. 


For the MVP, the simulation contribution consists of an identified robot model, a documented policy interface, verified environment behavior, and reproducible baseline measurements. These deliverables support the training team’s controller development and the embedded team’s implementation of compatible sensor and motor interfaces before zero-shot physical evaluation.

Data Generation
Purpose and Scope
Data generation for Zero Shot Balancer establishes the simulated conditions used to train and evaluate the robot’s controller. A policy that balances one robot configuration may respond differently when the mass distribution, available motor torque, or contact conditions change. The data-generation work therefore examines which variations can be represented by the simulator, how those variations affect the reference controller, and which conditions are suitable for further experiments.
The main inputs are MuJoCo XML Format (MJCF) models and configuration records describing physical parameters. These define the environments in which the policy operates. The observations, actions, rewards, and state trajectories are produced during interaction with those environments.
The completed work includes a configurable parameter-validation tool, boundary and mutation sampling, and four evaluation studies using a frozen reference policy. These studies provide evidence for selecting conditions for the broader evaluation benchmark. Movement schedules provide a complementary test by changing the requested speed and direction while the policy operates in a selected physical environment. The golden evaluation is intended to bring consistent test conditions into a benchmark used throughout the project and in the final evaluation.

Environment Generation and Boundary Sampling
MJCF Models and Configuration Records
MJCF is MuJoCo’s native XML-based language for describing a dynamical system. XML organizes information through named elements and attributes. In an MJCF model, bodies describe the system’s structure, joints define permitted relative motion, and geometric elements describe shapes used for visualization and contact. MuJoCo compiles the model description into the internal representation used by the simulator. 
For this project, that description represents the chassis, two wheels, their joints, the floor, and the actuators. Relevant settings include dimensions, inertial properties, contact friction, damping, and motor limits. MuJoCo can infer body inertia from geometric elements or use explicitly specified inertial properties, depending on the model’s compiler settings. Defaults and inference make the compiled result important: a number written in the XML is not sufficient evidence that the simulator uses it as intended. The reference inspection and conversion described above address this issue before the tool generates physical variations.
A configuration record describes how the project’s generation and evaluation tools should conduct an experiment. The input requests use JavaScript Object Notation (JSON), a text format that represents structured information through named values, objects, and arrays. JSON supplies the representation, while the project defines the meaning and permitted values of its configuration fields. The record identifies the property to vary, the sampling request, the evaluation seeds, and the computational limits. It can also provide dimensions and other settings for the supported robot topology.
The request, the generated model, and the outcome record serve distinct roles. One request can produce many candidate environments, and each environment can then produce several rollouts because it is evaluated across seeds. A generated case record connects the chosen parameter values with the model variant and its screening status. Saved trial results add the seed-specific observations and outcomes. Maintaining these links prevents a collection of XML files from becoming detached from the conditions under which its performance is measured.

Generating and Screening Configurations
The parameter-validation tool separates the experiment into model inspection, bound calculation, variant generation, trial execution, and reporting. Each operation produces information used by the next stage. The execution command coordinates the experiment, while the individual operations also allow the team to inspect the model or rebuild a report without repeating every trial.
The process begins by resolving the request and inspecting the configured baseline. Bound calculation then establishes the geometric and conditional restrictions, and variant generation assigns candidate parameter values. Each case has a record linking those values to the generated model and subsequent results. Cases excluded by mathematical screening remain recorded without a policy rollout. This preserves evidence of the search while avoiding simulation of candidates already rejected by the screening rules.
For admitted cases, the tool produces model variants and checks that the requested changes affect the compiled physics. This is particularly important for inertia, actuator limits, and contact properties, where changing a written value does not by itself show that the intended behavior changed. Keeping the nominal configuration in the generated collection provides a reference against which the mutation process can be checked.
The initial sampling includes endpoints, nominal values, and neighboring values around domain or exclusion boundaries. A one-axis center-of-mass sweep keeps the other coordinates nominal. A joint request evaluates combinations instead. The completed fore–aft/vertical request uses an initial 11-by-11 grid, with boundary neighbors and a budget of 12 additional refinement cases. This provides direct observations of interactions that separate one-axis sweeps cannot establish.
Refining Changes in Outcomes
After the initial trials, the tool identifies neighboring samples whose seed outcomes differ and evaluates intermediate values. Refinement follows observed transitions rather than assuming a single monotonic success threshold. It stops when the requested bracket width is reached or the declared case budget is exhausted. Consequently, the output is a set of sampled outcomes and transition brackets; unsampled regions remain unresolved.
Validation Protocol and Completed Findings
Qualifying the Reference and Classifying Outcomes
The experiments use the existing frozen reference PPO policy. Policy weights remain fixed, allowing the tests to examine how physical changes affect the same controller. Before property trials begin, paired runs compare the original and converted models through states, observations, and policy actions. A separate neutral baseline must then balance for the full evaluation duration on every requested seed without numerical anomalies or review flags. A failed baseline stops the sweep rather than triggering a policy substitution or retraining.
The neutral evaluation uses zero movement targets and a reproducible reset with small initial pitch disturbances. It removes the inherited artificial pitch bias, corrects reset quaternion ordering, and resets derivative history while reusing the reference observation and action conventions. Each reported property trial covers ten cumulative simulated seconds on one of seeds 0–4. A fall causes a seeded reset so the trial can finish its time budget. Full-duration balance, however, requires completing the trial without any fall.
These changes belong to the neutral validation profile used for the parameter studies. They do not establish that the active training environment has the same reset behavior or that its outstanding integration checks are complete. Keeping the validation profile identifiable allows the team to interpret its results alongside the separate simulation and training work.
Numerical validity and balance are evaluated separately. Nonfinite states, unexpected simulation-time changes, and simulator warnings can indicate numerical problems. Large finite measurements are recorded through separate review flags. These diagnostics inspect control-step endpoints and warning counters rather than every intermediate physics state. A numerically valid rollout can still contain falls, and a balanced rollout does not establish physical feasibility. The protocol also measures position drift, but its balance criterion is survival rather than precision position holding.

Data Quality Checks and Reproducibility
Preserving Experiments and Correcting Generation Errors
The validation implementation saves the request, bounds, case manifest, model variants, frozen policy, source snapshots, hashes, and dependency versions. Per-seed logs and full state/action traces support the summary tables and transition reports. Independent artifact verification checks hashes, seed and duration coverage, finite traces, and consistency between saved records. These records make an outcome traceable to the model and implementation that produced it.
Verification exposed a generation issue in the first vertical and joint studies: floating-point arithmetic produced an offset of approximately −1.39 × 10⁻¹⁷ m for an intended zero sample. The generator was corrected to snap machine-scale zero roundoff before deduplication, and a regression check requires exact nominal reproduction. Corrected studies were completed separately, preserving the earlier attempts. This demonstrated the importance of checking the nominal case against the baseline rather than relying only on the displayed parameter value.
Interrupted trials are also preserved. Three workers in the corrected joint study timed out; retries used the original saved sources and unchanged policy and dependencies. The aggregate selected one completed attempt per case and seed while retaining the partial logs. After the repository reorganization, 15 targeted neutral-protocol trial traces reproduced historical traces exactly. Those compatibility checks supported retaining the earlier findings without claiming that the full 725-trial study had been repeated.
Existing Command Data for Evaluation
Smooth and Hard Schedules
Physical configurations specify the robot and environment used in a trial. Command schedules specify the movement requested during that trial. The existing smooth and hard schedules supply repeatable changes in wheel-speed and yaw targets. These files are available inputs for evaluation and provide a starting point for the golden command dataset. The performance-evaluation section describes the metrics used to assess the resulting behavior.
Each schedule entry records an absolute start time and two target values. The evaluator holds the targets until the next entry, so both schedules are piecewise constant. The smooth schedule uses smaller successive changes; it does not continuously interpolate between entries. The smooth file contains 30 entries at two-second intervals, while the hard file contains 20 entries with larger changes, reversals, and turning requests. Both finish with an entry at 58 seconds and a two-second hold, producing a 60-second evaluation under the default timing.

The plotted values retain the current controller interfaces. The schedules use wheel-speed commands, and the supported environments do not interpret yaw identically: the Control Agent uses heading, while the reference uses a wheel-speed differential. The intended shared simulation and physical dataset uses target travel speed and direction, so its units and conversion to controller inputs still need to be finalized. The existing values cannot be treated directly as calibrated physical velocity limits.
Remaining Data Generation Work
Physical Configurations and Dataset Separation
The next stage applies the validation process to the selected robot model and completes the environment collections needed for training and evaluation. Updated dimensions, mass properties, and motor measurements will inform the parameter ranges. The completed studies identify useful test conditions and demonstrate the importance of checking combinations, but they do not yet constitute the final training, validation, and test datasets. Other supported properties also require experimental sweeps before the team can report controller outcomes for them.
The team plans to assign physical configurations to training and evaluation roles before using them for policy comparisons. Training conditions provide experience for learning, while validation conditions support development decisions. The benchmark records need to distinguish a new physical configuration from a repeated trial with a different seed. The intended tests also distinguish new combinations within the training ranges from values outside those ranges. Recording these assignments will make the scope of the generalization results clear.
Golden Command Dataset
The team plans to generate a 60-second golden command sequence containing a mix of smooth and demanding movements. It will include gradual and sharper turns, increases and decreases in velocity, and changes in yaw. This mix is intended to evaluate ordinary movement as well as the transitions that place greater demands on the controller. The existing smooth and hard schedules provide examples, but the final command magnitudes, timing, and ordering have not been fixed. The golden evaluation dataset will ensure fixed and specific features.
The remaining generation work includes selecting that sequence, checking its JSON records and total duration, and reviewing whether its demands are physically achievable. Feasibility depends on both the target and the time available to reach it. A sharp change in a requested target does not require an instantaneous change in the robot’s motion, and failure by the reference policy alone does not prove that a maneuver is impossible. The final sequence will be retained for repeated comparisons through the end of the project, with the associated physical configurations and evaluation settings recorded.
Because the golden evaluation is used repeatedly, the team must record whether its results influence training or checkpoint selection. A recurring development benchmark is not an untouched final test if its results guide those decisions. The remaining dataset specification therefore needs to identify which conditions serve development comparisons and which, if any, remain reserved for final testing. Any later change to the commands or physical configurations requires a new benchmark version so that comparisons remain interpretable.
Applying the Data Quality Plan
The team has prepared a data-quality testing plan for the generated environment collections. Applying it to the finalized datasets remains future work. The plan includes parameter summaries and histograms, coverage analysis, and checks for unintended relationships between parameters. The coefficient of variation describes relative spread but is unsuitable for offsets with means near zero. Centered discrepancy measures departure from uniform coverage after parameters are normalized to their intended bounds. Its interpretation must reflect the collection’s purpose: boundary-focused tests deliberately concentrate samples near limits rather than covering the domain uniformly.
The plan also identifies Spearman rank correlation for monotonic relationships and variance inflation factors for multicollinearity. Deliberate physical constraints must be considered when interpreting either measure. Sobol sensitivity analysis is a further planned study of how parameter variation contributes to a selected performance output, including interactions. It requires an appropriate sampling design and corresponding rollouts. These analyses will extend the completed checks on individual environments; no dataset-wide statistical results are claimed at this stage.

Pre-Training:
Algorithm and Policy Selection
Reinforcement Learning and PPO
For this project, reinforcement learning (RL) was chosen as the method to train the policy. RL is a process in which an agent learns through trial and error which actions lead to the highest reward [IBM RL]. In this case, the policy receives a reward from the environment after each action, and its objective is to maximize the cumulative reward over time. 
The technique used is Proximal Policy Optimization (PPO), since it provides stable training by limiting how much the policy’s behavior can change in each update, while being less computationally expensive than other approaches [PPO Paper]. It has also been used in related projects, including the open-source repository the team is using as a reference [Reference Repo].
For the reinforcement learning algorithm, the team started by using PPO as implemented in the RL framework Stable-Baselines3 (SB3) [SB3 Paper]. This ensures a cleanly designed and thoroughly tested implementation of PPO, which has also empirically been proven to work well on the reference open-source repository [Reference Repo], although for a slightly different problem and a different reward function.

The PPO policy is used as an agent, and the environment is a MuJoCo simulation of a two-wheeled robot. At every control step, the policy observes six values: the pitch angle, the pitch rate, the speed of each wheel, the speed error, and the yaw error (Table 6). The output is a command for each wheel that changes the wheel’s speed by up to ±4 rad/s. The full observation and action interface is described in the simulation section.

Reward Design
Reward Definition
In reinforcement learning, the agent learns only what the reward function encourages, and its main objective is to maximize this reward over time. The reward function is evaluated at every timestep and returns a number indicating how good the action was, these values are summed over an episode. Due to this, the design of the reward function has a big impact on the final behavior of the policy [IBM RL].
The reward function adapted from the reference project [Reference Repo] tracks the policy’s ability to adhere to the target velocity and target yaw. During training, the targets are randomly generated by the environment. The reward is a weighted sum of separate terms that encourage or discourage specific behaviors of the policy. Weights have different values, and this tells the policy of which behaviors are more important. Pitch has a small weight because the robot must lean to move. Unlike the other terms, lean can add or subtract reward. This is especially important because it rewards the posture the robot needs to change its speed. A two-wheeled balancing robot needs to lean forward to accelerate and backward to decelerate. This term rewards the policy for leaning toward the target velocity, scaled by the size of the velocity error, and penalizes leaning away from it.
Baseline Training Setup and Replication
Baseline Replication and Training
The repository [Reference Repo], was used as a baseline reference to build the team’s own policy. Only the files needed for training were copied into the project repository: the training command-line tool, the training environments, and the MuJoCo robot model they depend on. In addition, some changes were made to adapt it to the team’s setup. For instance, training was moved to the GPU (CUDA), and an optional limit on training timesteps was added.
The baseline policy was trained with PPO for 3,000,000 steps, using the default SB3 hyperparameters shown in Table 6 [Training Script]. According to the replication notes, it learns to balance reliably after about 200,000 steps. During training, the model is evaluated every 20,000 steps, and if it has improved, it is saved as the new best model. Snapshots are also saved every 40,000 steps, and each reward term is logged separately to TensorBoard.

Post-Training:
Post-training has not yet started, and this section describes the planned approach. It will begin once the pre-trained policy reaches the machine learning MVP. Its main goal is to improve the policy’s out-of-distribution generalization: its ability to keep balancing and tracking commands under physical conditions it was not trained on.
Fine-Tuning with Domain Randomization
After establishing a pre-trained policy under fixed simulation conditions, the team will continue training a copy of that policy on a collection of environments with varied physical conditions. This will be the fine-tuning stage. The fine-tuning dataset will consist of environment configurations and parameter ranges, such as different surface friction values, rather than a fixed collection of labeled examples. The actual training experience will come from the policy of interacting with these environments and receiving observations and rewards.
Training and Evaluation Datasets
For post-training, two new datasets will be created at the same time. The first is a training dataset with varied physical forces, which will be used to fine-tune the pre-trained model. The second is a separate evaluation dataset, used to measure how well the policy performs under physical conditions different from those it was trained on. This gives an estimate of how well it would transfer to the real robot built by the embedded team. The two datasets need to be kept separate so that the policy is evaluated on conditions it has not encountered during training. These datasets are described in the Data Generation section.
Physical Parameters
The team proposes sampling physical parameters within defined ranges at the beginning of each episode. Initially, one parameter will be varied at a time to understand its effect, and combinations will be considered once the individual environments behave as expected. The task, observation format, and action definitions will remain consistent so the policy can continue learning the same balancing and movement behavior across these variations. The original pre-trained checkpoint will be preserved for comparison, and the fine-tuning settings, training steps, and random seeds will be recorded.
Validation and Comparison
The fine-tuning environments will be separated from validation and final testing conditions. Validation will guide training decisions and checkpoint selection, while the final test conditions will remain held out from those decisions. The pre-trained and fine-tuned policies will be compared using the same test conditions and measurements, including balance duration and distance traveled before falling. Repeated runs will help determine whether an improvement is consistent. The goal is to improve performance under changed conditions without losing the ability to perform the original task. Once a policy is selected for final evaluation and physical deployment, its weights will be kept fixed so that generalization can be measured without additional training on the test conditions or the physical robot.
Dataset Quality
Before the generated environments are used for training or evaluation, their quality must be tested, so that the results reflect the policy’s performance rather than problems in the environments, such as unstable simulations or parameters that do not cover their intended ranges. The team researched several data quality tests to see which could best fulfill these requirements for the MJCF environments. These tests are described in the Data Generation section.
Dataset Scaling
The post-training dataset will involve a suite of training environments of the following sizes: 64, 128, 256, 512, and 1024. If 6 physical effects are chosen as parameters, then 64 environments represent one environment for each of the 2⁶ combinations, 128 represent two per combination, and so on. After every data scaling step, a test will be run against the full evaluation benchmark to understand how variance impacts out-of-distribution generalization across interpolation and extrapolation.
Risks of Post-Training
The physical variations must be realistic. If the ranges are too narrow, the policy may not handle the real robot; if they are too wide, it may become too cautious or adapt to conditions it will never face. The targets must also stay within the robot’s limits. In addition, the training and evaluation datasets must stay separate, so the evaluation measures how the policy handles new conditions, not ones it has already seen. Finally, the team also needs to be careful when fine-tuning the pre-trained policy. The main risk is forgetting while it adapts to new conditions, the policy may lose performance it had already achieved.

6. Performance Evaluations
   1. Purpose of Evaluation
The task that the robot is given is not only to remain upright, but to also follow a target speed and target direction as input from an external source. This task was chosen because it allows the engineers to develop an external, high-level controller with scalability. Target speed and target direction combine to make target velocity. A human pilot as the user or an autonomous algorithm could wield the high level controller to act as a navigation, guidance, or steering system for the robot. But no matter the type of system, from human operations to mechanical systems to software, it is critical to measure the quality of the solution made to address the core problem.

The core problem the team is solving is autonomous movement while remaining upright. The evaluation system measures the performance of the robot with the following metrics:

The quantity of data matters in the golden evaluation dataset. There are enough samples to make for an exactly 60 second testing runtime. Both the smooth and the extreme evaluation schedules are used for simulation development & performance measuring only. ML Development Life Cycle:
ML Team Phases
The machine learning portion of the project will follow five main phases: data generation, pre-training, post-training, evaluation, and deployment. These phases provide clear milestones for developing, testing, and transferring the reinforcement learning policy from simulation to the physical robot.
Phase 1: Data Generation and Benchmark Development
The first phase focuses on building the simulation environments needed for reinforcement learning. The primary artifacts will be MJCF files, environment configurations, parameter ranges, and scripts used to generate training conditions.
The team will first create a baseline MJCF model of the two-wheeled robot using MuJoCo. This model will include properties such as robot geometry, joints, actuators, mass, and surface friction. Measurements from the embedded team will be incorporated as the physical robot design becomes more finalized.
The team will then create three groups of environments: training environments, fine-tuning environments, and a held-out evaluation benchmark. Candidate variations include friction, payload, initial tilt, and external disturbances. Before training begins, the environments will be tested to verify that observations, actions, reset behavior, and termination conditions work correctly.
Deliverables: validated MJCF model, training and fine-tuning environments, held-out benchmark, and environment quality tests.
Phase 2: Pre-Training
The second phase focuses on developing the baseline reinforcement learning policy. During this phase, the team will finalize the model architecture, RL algorithm, reward function, and training recipe.
The reward function will encourage the robot to remain upright and move as intended while penalizing behaviors such as excessive tilt, falling, or unnecessary motor activity. Stable-Baselines3 will be used to train the policy in the baseline environments.
Performance will be monitored using validation environments, and the selected checkpoint will then be evaluated on the held-out benchmark. These results will serve as the baseline for later comparisons.
Deliverables: finalized architecture and algorithm, reward function, training recipe, trained baseline policy, and initial benchmark results.
Phase 3: Post-Training
Post-training will be used to improve the robustness of the baseline model if additional training is necessary. A copy of the baseline policy will be fine-tuned using environments with varied physical conditions.
Parameters such as friction, initial tilt, payload, or disturbances may be randomized between episodes. The team will first test individual variations and later consider combinations of parameters.
The original baseline policy will remain unchanged so that its performance can be directly compared with the fine-tuned model.
Deliverables: fine-tuned policy, documented training variations, validation results, and comparison against the baseline policy.
Phase 4: Evaluation
The evaluation phase will measure how well the final policy performs on the golden evaluation dataset and generalizes to unseen conditions. Before evaluation, the selected model weights and benchmark will be frozen.
The baseline and fine-tuned models will be tested using the same held-out environments. Metrics may include balance duration, distance traveled before falling, successful episode rate, and recovery from disturbances. Multiple runs will be performed to measure consistency.
These results will determine whether post-training improved robustness and whether the model is ready for deployment.
Deliverables: final benchmark results, baseline versus fine-tuned comparison, and selected deployment model.
Phase 5: Deployment
The final phase transfers the trained model from simulation to the physical robot. The selected model will be converted and quantized using TensorFlow Lite so that it can run on the robot's embedded hardware.
Regression testing will verify that conversion and quantization do not significantly change model behavior. The ML and embedded teams will also confirm that physical sensor observations and motor commands match the formats used during simulation.
Once these checks are complete, the policy will be deployed and tested on the physical robot under controlled conditions. The results will show how successfully the learned behavior transfers from simulation to the real system.
Deliverables: quantized TensorFlow Lite model, regression testing results, deployed policy, and physical Sim2Real test results.

Embedded Systems
An essential component of the project are the microcontrollers and sensors used on the robot. Given its scope, there were a few hardware requirements that demanded thorough research to align with the team’s design philosophy. The goal for the physical product is to be as compact as possible while having above adequate computational power to run a machine learning model.

ESP32
This microcontroller is a small dual-core processor capable of running up to 240MHz and     
 has 520KB of total SRAM, shared by firmware and the TFLite runtime. Additionally, 240MHz should be fast enough for the ESP32 to relay and receive information from other controllers and sensors on the robot.

Hardware Verification
Before working with any of the peripherals, it is integral to the project’s success to assure that they work appropriately. An issue with hobbyist microcontrollers and boards is fault products, counterfeit technology, or clone boards that do not work as advertised. Dealing with faulty hardware is a preventable situation that calls for verification.

To accomplish this,  the embedded team verifies if each board works by uploading trusted and working code to measure the peripherals’ baseline. For the IMU, the team needed to verify the position it reports is accurate and can determine it is moving. This was confirmed via logs on a serial monitor while the IMU was put under set conditions. Along with that, the motor encoders will be put under its own set conditions to also confirm it is reading the motor axle’s position and speed accurately.


The peripherals’ readings are verified manually to guarantee that they are working as advertised and will not cause issues in the project. 


Firmware Architecture
The heart of the physical robot is the firmware running on the ESP32. The plan is creating three layers that handle hardware abstraction, services, and applications where dependencies flow down whereas data flows bidirectionally. Each layer isolates different aspects of code to help with cleaner development, easier debugging, and seamless integration while also letting the team easily switch hardware. 
Figure 8 Proposed three-layer firmware architecture showing application, services, and drivers, with downward dependencies and bidirectional data flow.  


Hardware Drivers
This layer handles the abstraction of all hardware on the robot. As mentioned before, the robot uses an IMU and motor encoders to balance itself. The code here will be derived from open-source libraries and be modified as needed. By making use of abstraction, the team does not need to address registers to configure the IMU or motor encoders.

Services 
This layer focuses on actions the robot can do, hence the layer name services. This layer uses functions from the hardware driver layer to create behaviors the robot can do. For the project, it is imperative for the robot to 

- build vectors describing the robot’s real time position to feed to the ML model
- estimate the wheel’s velocity using the IMU’s accelerometer 
- make decisions based off of real time IMU data via a policy controller 
- generate logs for debugging and telemetry purposes

These actions will be orchestrated by an additional layer in the main control loop.

Application 
This layer orchestrates what actions the robot will do via a main control loop. It also will be the place where the robot can override any faulty actions the ML model decides to perform to prevent damage to the robot chassis and hardware.

Memory and Resource Constraints
Limited memory is the biggest concern with any project containing embedded systems. The limited resources means optimizing code and compressing the model such that both can successfully run without bogging down the ESP32. The team’s ESP32 has 520KB of total SRAM, but the model’s runtime memory budget must leave room for firmware, stacks, and buffers. There is an additional 4MB of built in flash storage for the entire project’s firmware. The team is anticipating using well below the allotted memory even without optimization but will prioritize having quality code to reflect what is seen in industry.

Another major concern is how fast the CPU cycles are on the ESP32. The ESP32 can run at up to 240MHz, or 240,000 clock cycles per millisecond. The sensor sampling rate and control-loop update rate are separate from the CPU clock rate; the CPU does not need to run at the IMU’s rate. The microcontroller must read the data off the IMU, interpret it, and respond accordingly within each control-loop period so that the robot balances. Keeping track of this number is especially important when training the ML model because whatever control-loop update rate the physical robot uses, the model must be trained under those conditions as well.

Designing Around Integration
The firmware is designed with integration in mind. This means assuring that each component works together and agrees on units, timing, and data formats.
The team uses the following across the firmware and in communication with the ML team so that the they use the following in their training pipeline:
- Angles measured in degrees with the zero point set at [TBD when calibrating robot]
- Angular rates in deg/s
- Wheel velocity in rad/s but is subject to change based off of encoder readings
- Time measured in ms

Additionally, timing should be shared across all layers in firmware architecture. For example, instead of isolating a sensor reading within a clock cycle, each reading should be relative to each other's time and build a context around it. Doing so provides a pool of behaviors that describe what the robot is doing in real time. This means the model does not respond to a single sensor reading but rather a description of what the robot is sensing within a given set time. Under this logic, the firmware should be able to generate an average on the robot’s position and speed within a set time for the model. At the moment, this set time is undetermined. The team can use the known information on CPU clock rate to find a theoretical time, but ultimately, trial and error will be the best way to find the set time that works for the robot.

While the goal is to accomplish a seamless integration, inevitably, there will be issues. This can vary from changing the robot’s firmware configuration, altering firmware to better interact with the ML model, or retraining the model to accommodate any firmware or physical changes to the robot. While the team is anticipating these problems, designing quality firmware with good traces will help navigate the integration phase efficiently.

Custom CAD Design
To ensure this project's success and originality, the hardware team chose to CAD the main chassis, as well as any secondary, attached parts that may require it. This work uses the free-for-student online web-based CAD platform, Onshape. the team has developed the chassis and worked through its printing, physical assembly, and the measurements and exports shared with the machine learning team. The design has changed as each of those steps provided information that was not available at the start.
The Initial Bill of Materials and Embedded Systems sections describe the hardware configuration and component requirements. For the chassis, the immediate questions are where the parts fit and whether they can be installed and reached. The motor brackets need secure mounting surfaces, the wheels need clearance, and the electronics need accessible mounting space. A part that fits in the assembly model can still be difficult to fasten once another platform is in the way.


An open design with structural supports shifted to the outside of the chassis was chosen for maximum accessibility to internal components. Outside guides and/or holding mechanisms to keep wires, looser parts, or electronics from slipping or falling out during fast movement and in the event of a collision remain under consideration as the build develops. These are possible additions to the chassis; they have not all been implemented in the printed prototype.
the team uses representative component models in the full CAD assembly to consider their sizes and placements together [CAD History]. Some of those models were approximations before the actual hardware arrived. Printing then introduced orientation and connection problems, while assembly revealed fit, tool-access, and ground-clearance issues. the team has used those observations to revise the chassis. The mechanical work has reached a partially assembled v1.1 build and a v2 print in progress; controlled balancing remains a separate integration step.
The preliminary design of the custom 3D-printed chassis established the structural arrangement and representative hardware. Before the detailed custom assembly was finished, the team used this model to determine how the wheels, motors, platforms, and supports could occupy the same structure. It did not yet represent every board or mounting detail that appears in the later design.
Because the physical parts had not arrived, the team used estimated sizes and comparable open-source component models to develop the layout. This allowed us to continue the CAD work while leaving room for correction. The limitation was straightforward: a similar bracket or motor model could help establish space, but its dimensions could not guarantee that the ordered part would slide into a printed mount. The preliminary geometry served as a starting point for the detailed chassis rather than a final fit specification.

Upper Mass and Cowboy Hat Integration
The initial plan placed the larger, heavier components (motors and battery pack) near the bottom to limit how much they raised the overall center of mass. That placement rationale still left a question about the amount of mass in the upper structure. For the selected robot design, the team considered the initial upper mass too small. the team therefore chose the cowboy hat as a unified upper feature that would add material near the top and center while remaining part of the printed chassis.
the team has not yet tested whether the hat improves balancing. Adding upper mass changes the mass distribution, so the team needs to evaluate its effect with the rest of the robot and its controller. the team will include its contribution in the updated mass properties and evaluate it when the robot is ready for balancing tests.
The hat also required more CAD work than simply placing an object on top of the supports. The starting model was downloaded mesh geometry. An STL file describes a surface with triangles, which behaves differently from a native solid built from sketches and features. Onshape supports references to imported meshes and some operations on mixed mesh and solid geometry, but the available operations depend on the geometry involved [Onshape Mesh Guide]. This difference became a practical obstacle during integration.
the team worked through the mesh problems by repairing non-manifold edges, using Blender in the export workflow, and finding a way to integrate the result into Onshape. Non-manifold edges are mesh connections that do not form a consistent surface boundary. Repairing those connections was part of making the downloaded model usable in the chassis workflow. The Onshape history records the team's insertion of the cowboy-hat-tray STL on October 1 [CAD History].
the team retained the resulting upper feature in both the v1 drawing and the later assembly. the team also needs to include the intended printed hat in the mass estimate without counting an overlapping duplicate as additional physical material. Earlier export and mass notes distinguish an included chassis hat from an extra overlapping occurrence that was omitted.

the team needs to keep the saved files in context. Mass Properties and Simulation Measurements
the team supplied the machine learning team with robot dimensions and center-of-mass information to help connect the physical design with its simulation. The local mass workbook documents an earlier assembly estimate using fourteen component entries [Mass Workbook]. It combines component masses with estimated positions to obtain the overall center of mass. For each coordinate, one multiplies each component's mass by its coordinate, sums those products, and divides by the total mass.
the team needs to distinguish these estimates from physical measurements. Several component masses were assumed or based on comparable parts, and the component centers were estimated from bounding-box midpoints. The chassis input came from a recorded slicer estimate. A bounding-box midpoint describes the center of the outer dimensions; it does not necessarily describe where the actual mass is concentrated inside a motor, battery holder, or infilled printed part.
The earlier assembly estimate totals 945.16 g. Relative to the chassis-bottom origin, its calculated center of mass is X = -0.708 mm, Y = -0.055 mm, and Z = 60.565 mm. The displayed precision comes from the calculation and does not imply equivalent measurement accuracy.
the team also needs to provide the frame of reference with these values. The listed Z coordinate is measured from the chassis-bottom origin, while the workbook also provides a different height relative to its estimated ground plane. Neither should be substituted for the distance above the wheel axis without accounting for the geometry. The workbook also notes a difference between the wheel model's measured diameter and its nominal name, which needs to be reconciled with the actual wheels.
These results predate v2, so the team needs to recalculate them for the new chassis. Revised supports, mounting regions, connectors, and infill can change the printed mass and its distribution. The earlier workbook remains useful as a record of the calculation method and a starting point for the simulation team. the team will need an updated estimate and physical measurements where possible to describe the new robot.

Obtaining Data
        Unlike other forms of machine learning, the data used in reinforcement learning comes from the agent’s interactions with the environment. The environment that Zero-Shot Balancer is trained in is Gymnasium and MuJoCo, which are detailed in the simulation section of this document. However MuJoCo does allow for external environment files denoted as MJCF files, which are in the form of XML files that MuJoCo accepts as parameters for the physics engines’ dynamics. The XML files that the team leverages to achieve the MVP come from an Open Source github repository. There are also python files that interact with the MJCF files that allow the agent to receive further information from the environment, these are created by the engineers. Finally, for post-training there are many MJCF files synthetically generated by the engineering team for domain randomization of physical parameters. This is further detailed in the Data Generation section of this document.
        
Training
In reinforcement learning, there is no fixed collection of labeled examples. The training experience comes from the policy interacting with the simulated environments and seeing how much reward the robot gets. The team uses Proximal Policy Optimization (PPO), implemented in Stable-Baselines3, which collects 2048 steps of this interaction and then uses them to update the policy, repeating this process throughout training (see the Pre-Training section).
Training is divided into two steps: pre-training and post-training. In pre-training, the policy is trained under fixed simulation conditions until it reaches the machine learning MVP on the golden evaluation dataset. The policy is rewarded for staying upright and following the target speed and heading (see the Reward Design section). In post-training, the team will continue training a copy of the pre-trained policy on the training dataset with changing physical conditions created through the data generation work. This will be the fine-tuning stage (see the Post-Training section).
To choose the best policy, the model is evaluated every 20,000 steps during training. If the results of the evaluation show an improvement, it is saved as the best model. After training, each policy is compared with the reference baseline using the same measurements. The total reward is a comparable metric because the engineering team worked to fix the same reward within evaluation, despite reward shaping in training. In addition, a change in the reward or the observations is only kept if it improves these measurements, as was done in the Control Agent experiments (see the Training Experiments section).
Validation will help the team make training decisions and choose the best checkpoint. The evaluation datasets, such as the golden evaluation dataset and the final evaluation, will not be used for training. This way, the policy is tested on conditions it has not seen before. Once a policy is chosen for the final evaluation and the physical robot, its weights will be kept fixed. This allows the team to measure how well it generalizes without training it again on the test conditions or on the physical robot.
Selecting the model and shaping prompts
The Zero-Shot Balancer project does not use any generative AI component within the project. The engineering team does leverage generative AI effectively through the interfaces of chat completion LLMs and LLM based coding agents. For chat completion LLMs, prompts are shaped as needed to fit the question being asked so that the engineer learns all they can from the internet’s knowledge. For LLM based coding agents, prompts are shaped so that code changes are small and precise, which makes both reviewing easier and lowers the risk surface area for hallucinated or misinformed code changes.

        The team will have two separate MVPs before integration in the first semester of this course, one for the ML team and one for the embedded team. The team determines that for the project to be considered done it will need a functioning physical robot, a simulation-trained controller, and successful integrations of these two systems at the end of Senior Design II.         Aside from the integration, the MVP for the physical robot includes the assembly of the chassis, wheels, motors, battery pack, microcontroller, and sensors. Each of these components are mounted onto the 3D printed frame and allow the wheels to move without being interfered with by the body of the robot. The embedded team verifies the sensor readings, encoder measurements, and motor operations before the simulation model is integrated onto the hardware. The machine learning team has their own MVP aside from the larger goal of integration. The team aligns that for this MVP a trained policy needs to accept the defined observations and generate the required movements of the wheels. The golden evaluation benchmark will be used to evaluate the results of the simulation. The model checkpoint is identified and associated simulation settings will be then used for the deployment. 
        
Design Process for Physical MVP
On the physical side of the project, the team is prioritizing getting a Minimum Viable Product as quickly as possible in two phases: initial build and machine learning integration. The initial build and operation with reference firmware is the Senior Design I MVP while deployment of the ML team’s model is the integration milestone of Senior Design II. There are existing kits, open-source designs, and existing codebases that dictate how to properly build a two-wheel balancing robot. To ensure that the project has sufficient depth, from the beginning, the team decided to take on the bulk of the design with a custom system. This includes custom CAD and physical engineering and custom firmware that will be written specifically for the team’s exact robot. This means that a large part of the MVP revolves around hardware design. The team is approaching this step-by-step with adequate preparation time for the whole system. This means that parts are to be researched and discovered first so that they may be ordered with much advance shipping time.

During this process, the CAD and physical engineering that cannot be ordered will be completed. This is done in Onshape and printed on a 3D printer that the team has access to, with PETG or PLA filament, depending on the research done and what is needed for the project. Multiple iterations for the physical robot are expected. There is enough room for error for parts to be the wrong size that would affect the placement of hardware on the robot. This could affect the center of mass for the robot which would require the ML model to be retrained. 


Designing and 3D printing a robot specifically for this project gives the team full control over other things too. Modeling each hardware component and assembling it in the robot gives the team accurate information needed for efficient training on the ML model. The team also has access to 3D models of the robot to be trained on with a robot specific center of mass, an important piece of data for a self balancing robot. A 3D model allows for both teams to work asynchronously without a physical robot and make significant progress before the robot is physically available. 

Once the physical robot is available, it is anticipated to go through multiple iterations. This is to be expected in anything 3D printed due to tolerances and physical factors that affect a physical output but not the virtual one. Consequently, change will be made to the 3D model to fix any issues and the files will be given to the ML team so that they can retrain their model based off of the new changes. The design pipeline for the physical MVP provides a streamlined process for others to not be blocked on their tasks while still providing flexibility to make any changes accordingly. 

 
Expected Outcome for Physical MVP
        The second phase of the physical MVP to be completed during Senior Design II is machine learning integration, where the team intends to directly map the simulation neural network and machine learning protocols to the physical robot. This will be done by ensuring maximum communication & compatibility with the machine learning team from the start to initialize physical constants that will be present on the final physical robot (weight, center of mass, torque).
        The team intends to have this physical MVP as quickly as possible with as much accuracy as possible. Thanks to early experiments showing that the simulation is quite capable of performance as intended, the team expects the physical MVP to follow suit quickly. This is due to the design pipeline, which has allowed for the ML team and Embedded team to work without a physical robot because the team’s 3D model provided both teams with enough data to work with. The rapid development of the physical MVP brought forth issues the team didn’t anticipate. During the first attempt at assembly, the robot was too close to the ground because the tires it used were minorly deflated when it held the robot’s weight. As the robot continues to be worked on, it is anticipated to have more issues that will require redesigns. All of this is necessary to meet the team’s physical MVP. 

With a properly assembled robot, it is ready to be equipped with a ML model. This is because the robot is fitted with hardware that gives it the ability to determine its own position, speed, and wheel speed. It provides memory to hold the ML model that will give the robot the ability to respond to external stimuli using the robot’s collected data. 

It is expected for the physical robot to be able to balance itself at least 50% of the time only using the ML model. While the physical product is part of that MVP, it alone will not keep the robot balanced. The robot’s firmware flashed into the hardware will do the heavy lifting. It will provide the robot with the ability to “sense” its surroundings using selected sensors such that the ML model can act accordingly based on those readings. 

The success of the MVP relies on quality firmware, efficient physical design, and seamless integration between the firmware and ML mode. 


Design Process for Machine Learning MVP
The machine learning team first replicates the results from an open source repository containing reinforcement learning code for a self balancing robot to establish a baseline control reference. The design process begins by constructing a golden, quality tested evaluation benchmark scheduled with specific timestamps, target speeds, and target directions. Systematic experiments are then conducted on the control model to iteratively improve its performance against this established evaluation benchmark. Once the minimum viable product threshold is achieved, specifically requiring a minimum of over 50% upright survival time on the evaluation benchmark, the team proceeds to execute comprehensive ablation studies. These intensive studies require a factorial volume of testing to evaluate all possible combinations of parameter modifications, thereby ensuring a rigorous causal understanding of each experimental change.
Expected Outcome for Machine Learning MVP
The machine learning team engineers and trains a software controller via reinforcement learning within a physics simulation environment, where the algorithmic model functions as an active agent. The minimum viable product requires constructing an evaluation benchmark within the simulation that tasks the agent with three primary operational objectives: maintaining self balancing stability, tracking an input target speed, and matching an input target direction. The expected outcome for the minimum viable product is to successfully achieve over fifty percent upright survival time on the golden evaluation benchmark, alongside minimized error in target speed and minimized error in target yaw. Once the simulation trained agent meets or exceeds this required survival threshold and performance profile, the machine learning minimum viable product is officially achieved.
Potential Machine Learning Stretch Goals
Development on a comprehensive evaluation dataset containing varied physical parameters such as center of mass offsets, actuator strength limitations, terrain slopes, surface friction coefficients, and wind resistance is already underway. The primary stretch goal focuses on testing the out of distribution generalization capabilities of the trained agent. This evaluates the capacity of the agent to perform effectively on entirely unseen physical configurations, representing a core machine learning challenge that correlates theoretically with robust real world deployment under dynamic physical conditions.
Current timeline and milestones 
The team has created timelines to give an understanding of where progress should lie throughout the courses of Senior Design I and Senior Design II which takes place in the Fall of 2026 to the Spring of 2027. As the development teams are split until machine learning and embedded teams, there are parallel goals including integration milestones between the two teams. During Senior Design I the guidance was given that the team should produce a basic product and then during Senior Design II that product will be actually refined into a useful project deliverable. With that in mind the first semester goals are around establishing the simulation, training pipeline, building the first physical robot, and the first parts of integration between the two teams. The second semester is where the integration will be fully complete into one system, there will be full evaluation testing on the robots performance, and preparing for presenting this product. The first semester also involves heavy research and the second semester will focus on implementing that research into the project.
